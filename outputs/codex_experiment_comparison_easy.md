# Codex 실험 비교 쉬운 설명

## 한 줄 요약

친구 프로젝트는 **“항상 잘 돌아가게 만들자”** 쪽이 강했고,  
내 프로젝트는 **“내가 원하는 서비스 느낌으로 계속 다듬자”** 쪽이 강했다.

그래서 친구 결과물은 더 단순하고 안정적이고,  
내 결과물은 UI와 데이터 구성이 더 많이 바뀌었다.

## 어려운 말 쉽게 풀기

| 어려운 말 | 쉬운 말 | 뜻 |
|---|---|---|
| runnable invariant | 항상 되는 실행 방법 | 뭘 고쳐도 “이 명령어는 항상 돌아가야 한다”는 기준 |
| thin vertical slice | 작게 끝까지 만들기 | 데이터 수집 조금부터 화면 표시까지 작게 완성하는 방식 |
| fallback | 대체 화면 | 데이터가 없거나 실패했을 때 보여주는 임시 화면 |
| non-fatal failure | 실패해도 전체는 안 죽음 | 뉴스 하나 못 가져와도 웹페이지 생성은 계속됨 |
| config | 설정 파일 | 뉴스 주소나 검색어를 코드 밖에 적어두는 파일 |
| source | 데이터 출처 | 뉴스나 숫자를 어디서 가져왔는지 |
| pipeline | 작업 흐름 | 수집 -> 가공 -> 저장 -> 화면 표시 순서 |
| renderer | 화면 만드는 부분 | JSON 데이터를 HTML로 보여주는 코드 |
| dedupe | 중복 제거 | 같은 뉴스가 여러 번 나오면 하나만 남기는 것 |
| market scope | 다룰 시장 범위 | 국내, 미국, 금리/환율/유가 중 어디까지 볼지 |

## 친구 프로젝트와 내 프로젝트의 차이

| 구분 | 친구 프로젝트 | 내 프로젝트 |
|---|---|---|
| 중심 생각 | 일단 매번 실행은 잘 되게 만들자 | 원하는 서비스 느낌으로 계속 바꿔보자 |
| 구조 | 한 개의 실행 파일 중심 | 수집, 가공, 화면 파일이 나뉨 |
| 데이터 범위 | 국내 / 해외 | 국내 / 미국 / 금리·환율·유가 / 섹터 |
| 뉴스 출처 | 정해진 RSS 주소 | Google News RSS, 미국 영어 뉴스, 번역 |
| 화면 느낌 | 단순 헤드라인 목록 | 리포트형 브리핑 화면 |
| 장점 | 안정적이고 따라 하기 쉬움 | 더 제품처럼 보이고 요구사항 반영이 잘 됨 |
| 단점 | 화면이 심심할 수 있음 | 구조가 더 복잡하고 바뀐 내용 추적이 어려울 수 있음 |

## 내가 배우면 좋은 점

| 배울 것 | 쉬운 설명 | 왜 좋은가 |
|---|---|---|
| 항상 실행되는 명령어를 정하기 | “이거 하나 돌리면 결과가 나와야 한다”를 정해두기 | 작업이 길어져도 망가졌는지 바로 알 수 있음 |
| 결정 기록하기 | “왜 이렇게 만들었는지” 짧게 적어두기 | 나중에 다시 봐도 이유를 알 수 있음 |
| 가짜 데이터 조심하기 | 샘플이 실제처럼 보이지 않게 하기 | 진짜 데이터인지 헷갈리지 않음 |
| 뉴스 주소/검색어는 코드 밖으로 빼기 | 설정 파일에 따로 적어두기 | 나중에 바꾸기 쉬움 |
| 작게 고치고 바로 확인하기 | 한 번에 크게 바꾸지 않기 | 어디서 망가졌는지 찾기 쉬움 |

## 친구 workflow에서 굳이 따라하지 않아도 되는 점

| 따라하지 않아도 되는 것 | 이유 | 더 좋은 방식 |
|---|---|---|
| UI를 너무 나중에 보기 | 결과물이 기능은 되지만 재미없고 딱딱할 수 있음 | 초반부터 실제 화면도 같이 확인하기 |
| 국내/해외처럼 너무 넓게 나누기 | 내가 원한 건 결국 국내/미국/금리·환율·유가였음 | 처음부터 보고 싶은 시장 범위를 더 구체적으로 말하기 |
| 임시 데이터를 오래 남기기 | 진짜 데이터인지 샘플인지 헷갈림 | 데이터가 없으면 “데이터 없음”으로 보여주기 |
| 문서를 너무 많이 만들기 | 작은 프로젝트에서는 문서 관리가 귀찮아질 수 있음 | 꼭 필요한 문서만 유지하기 |
| 안정성만 보고 제품 느낌을 미루기 | 작동은 하지만 쓰고 싶은 화면이 아닐 수 있음 | 기능과 화면을 같이 다듬기 |

## 앞으로 자율 코딩 에이전트를 더 잘 쓰는 법

### 1. 먼저 “항상 되는 실행 방법”을 정하기

예시:

```text
이 프로젝트는 아래 명령이 항상 성공해야 한다.

python collectors/news.py
python collectors/prices.py
python processing/build_briefing.py
```

이렇게 말하면 에이전트가 뭘 고치든 마지막에 확인할 기준이 생긴다.

### 2. 중요한 결정은 짧게 적게 하기

예시:

```text
중요한 결정을 하면 DECISIONS.md에 짧게 적어라.
왜 이 방식을 골랐는지, 어떤 방식을 버렸는지도 적어라.
```

그러면 나중에 “왜 이렇게 만들었지?”를 덜 겪는다.

### 3. 가짜 데이터는 화면에 오래 두지 않기

예시:

```text
fake/sample 데이터를 실제 데이터처럼 보여주지 마라.
데이터 수집이 실패하면 가짜 값 대신 데이터 없음 상태를 보여줘라.
```

시황 서비스에서는 이게 특히 중요하다.

### 4. 설정은 코드 밖으로 빼기

예시:

```text
뉴스 검색어와 RSS 주소는 코드 안에 박지 말고 config 파일로 분리해라.
```

그러면 나중에 소스를 바꾸기 쉽다.

### 5. 화면 취향도 초반에 말하기

예시:

```text
UI는 단순 대시보드보다 The Daily Markets Brief 같은 리포트형 브리핑 느낌으로 만들어라.
```

이렇게 말하면 에이전트가 기능만 만들고 끝내는 일을 줄일 수 있다.

## 결론

친구 방식에서 배울 점:

- 항상 돌아가는 실행 명령을 정하는 것
- 작업 이유를 문서로 남기는 것
- 외부 데이터 실패에도 결과물이 나오게 하는 것

내 방식에서 살릴 점:

- 요구사항을 계속 다듬는 것
- UI 취향을 반영하는 것
- 실제 서비스처럼 보이게 만드는 것

가장 좋은 조합은:

> 친구 방식의 안정적인 작업 운영 + 내 방식의 제품 감각 반영

즉, **잘 돌아가게 관리하면서도, 내가 쓰고 싶은 모양으로 계속 다듬는 것**이 자율 코딩 에이전트를 잘 쓰는 방향이다.
